## Caveats, Assumptions, Limitations, and Future Work in SuperNova

Based on the SuperNova paper, the authors explicitly state several assumptions, limitations, implementation simplifications, and directions for future work, organized as follows:

---

### Theorem and Construction Assumptions

* **Size Bounds on Generator Algorithms**: The authors globally assume that generator algorithms producing public parameters are provided with appropriate size bounds [1].
* **Recursion Overhead Amortization**: The folding approach assumes a sufficiently large computation (specifically, at least 10,000 constraints performed at each step) to successfully amortize the recursion overheads [2].
* **Random Oracle Model**: The security of the underlying folding scheme is analyzed and proven secure in the random oracle model, assuming all participating parties have access to a random oracle [3].
* **Random Oracle Instantiation**: For the non-interactive folding scheme for committed relaxed R1CS in the plain model, the authors rely on Assumption 1, which assumes the existence of a non-interactive folding scheme with $O_{\lambda}(1)$-sized commitments [4].
* **Identical Circuit and Input/Output Sizes**: In the core construction of non-uniform IVC (Construction 1), the authors assume without loss of generality that the polynomial-time functions $F_1, \dots, F_{\ell}$ have identical input/output sizes and circuit sizes [5].

---

### Security

* **Cryptographic Hardness**: The paper uses the terms 'proofs' and 'arguments' interchangeably, meaning that soundness is a cryptographic argument that holds only under cryptographic hardness assumptions [6].
* **Proof Size and Zero-Knowledge Limitations**: The raw proof size at the end of $N$ steps is proportional to the sum of the sizes of the circuits for the functions in $\{F_1, \dots, F_{\ell}\}$ and is therefore not concretely small [7]. Additionally, this raw proof is not zero-knowledge [7]. To obtain compressed proofs and achieve zero-knowledge, a general-purpose zkSNARK (such as Spartan) must be invoked [8].

---

### Performance and Implementation Simplifications

* **Sizing Issue of Running Instances**: In a naive implementation, because $U_{i+1}$ is produced as the public input/output (IO) of $F'_{pc_{i+1}}$, it must be contained in the public IO of instance $u_{i+1}$ [9]. In the subsequent iteration, because $u_{i+1}$ is folded into $U_{i+1}[pc_{i+1}]$, the properties of the folding scheme dictate that $U_{i+1}[pc_{i+1}]$ must be at least as large as $U_i$, causing the size of the running instances to grow at each step [9]. To alleviate this, the authors simplify the implementation by having each $F'_j$ only output a hash of its outputs, with the subsequent step taking a preimage to this hash as non-deterministic input [10].
* **Base Case Handling**: The high-level overview of the prover's work intentionally overlooks minor complications, such as not defining a base case proof $\Pi_0$ or specifying how the prover, verifier, and each function $F'_j$ handle the base case [11].
* **Additional Prover Advice**: The verifier of the non-interactive folding scheme run by $F'_j$ requires additional advice generated by the folding scheme's prover, which is addressed by having the prover provide additional non-deterministic input to $F'_j$ [12].
* **Hash Cost Scaling**: In the construction of $F'_j$, the cost of hashing scales with the number of supported instructions $\ell$ because the circuit takes $\ell$ running instances as non-deterministic input, even though only one instance is updated per invocation [13]. While this can be optimized to $O_{\lambda}(1)$ constraints using multiset-based offline memory checking, this is presented as an optimization rather than the default construction [14].

---

### Experimental Scope

* **No Experimental Evaluation**: The provided pages of the paper do not contain any experimental evaluation, implementation results, or empirical performance measurements. The scope of the provided text is entirely theoretical, focusing on definitions, constructions, and mathematical proofs of completeness, knowledge soundness, and efficiency.

---

### Future Work

* **Parallel Proof Generation**: SuperNova does not immediately support parallel proof generation [15]. Although a generic compiler exists to transform such constructions to support parallel proving, the authors leave the development of a tailored parallel proving solution for SuperNova to near-term future work [16].
* **Formal zkSNARK Details**: The authors explicitly defer the formal details of the zkSNARK of valid NIVC proofs to near-term work [17].
